# 开发重难点总结

> 本文件按「完成一部分记录一部分」的方式持续追加。每个小节记录该部分的**关键难点、踩过的坑、以及最终解决方案**，供后续维护与面试复盘使用。

## 第一部分：基础框架 + 模块 003 用户鉴权

**范围**：统一配置/异常/日志/DB 会话/8 张数据表/init.sql/应用入口；注册、登录、JWT、每日配额、管理员预置。

### 1. Python 3.14 环境兼容（重大环境难点）

- 项目采用 **Python 3.14**（全量统一为 3.14，本机唯一版本）。以下库曾因 cp314 预编译轮子踩坑：
  - `ahocorasick-ng`（C 扩展）：**3.14/Windows 下无任何发行版**（`pip install` 报 `No matching distribution found`，连 sdist 都没有）→ 改用同 API 的**上游包 `pyahocorasick` 2.3.1**（有 `cp314-win_amd64` 轮子，实测安装成功，导入名同为 `ahocorasick`，详见 docs/安装教程.md §1），**无需自研**。
  - `passlib` + `bcrypt>=4.1`：passlib 会读 `bcrypt.__about__.__version__`，该属性在 bcrypt 4.1+ 已删除 → 直接用 `bcrypt` 库（同一算法，无兼容层更稳）。
  - `chromadb`：**实测可装（1.5.9）**，万幸。
- 结论：升级前先 `pip install` 试一遍，发现缺轮子立刻调整技术选型或改用可装的上游替代，不要在文档阶段才发现。

### 2. PyJWT 2.x 强制 JWT `sub` 声明为字符串

- 数据模型里写的是 `"sub": 42`（int），但 PyJWT≥2 校验时抛 `InvalidSubjectError: Subject must be a string`（符合 JWT RFC）。
- 解决：签发 `sub=str(user_id)`，解码后 `int(payload["sub"])` 转回；`deps.py` 里对 `sub` 解析失败兜底抛 401。

### 3. SQLite（测试）与 MySQL（生产）的差异

- **BIGINT 主键不自增**：SQLite 只有 `INTEGER PRIMARY KEY` 才作为 rowid 别名自增，`BIGINT` 主键插入时 NOT NULL 失败。
  - 解决：`_PK = BigInteger().with_variant(Integer, "sqlite")`，MySQL 下仍是 BIGINT，SQLite 下退化 INTEGER。
- **内存库连接隔离**：SQLite `:memory:` 默认每个连接一个独立库，多线程/多连接会互相看不到表 → 用 `StaticPool` 让所有连接共享单连接。
- **ENUM / JSON 可移植**：SQLAlchemy Enum 在 SQLite 生成 VARCHAR+CHECK，JSON 生成 TEXT，均可用，生产仍是原生类型。

### 4. bcrypt 72 字节输入上限

- bcrypt 对 >72 字节输入直接抛 `ValueError`（bcrypt≥5 收紧）。注册时需**先校验密码长度 ≤72 字节**再哈希，否则恶意超长密码会让接口 500。

### 5. 登录防枚举 + 暴力破解防护

- **统一失败提示**：账号不存在与密码错误返回同一条 `invalid_credentials`，防止账号枚举。
- **递增延迟**：按「账号+IP」内存态记录连续失败次数，`fail_count ≥ threshold`（默认 5）触发锁定 `min(2^fail_count, 300)` 秒；登录成功清零。
- 已知限制：内存态重启丢失、多实例需 Redis（写入 data-model 已知限制）。

### 6. 模块级单例在测试间泄漏状态

- `login_guard` 是模块级单例，跨测试保留失败记录 → 后续测试被前一个测试"锁住"。
- 解决：conftest 加 `autouse` 夹具在每用例前后清空 `login_guard._records`。**任何模块级状态都要在测试隔离阶段考虑**。

### 7. 管理员账号不能在 SQL 里预置

- bcrypt 哈希必须由应用生成，不能在 init.sql 里写死明文 → 管理员由**应用启动时**按 `.env ADMIN_ACCOUNT` 预置（存在则置 admin 角色，不存在则以 `ADMIN_PASSWORD` 创建），生产提示改密。

### 8. 统一异常 → 契约错误码

- 所有受控错误走 `BizError` 子类（带 status_code/code/message），FastAPI 全局处理器统一转 `{"code","message",...}`，与各模块契约的错误码表一一对应，前端可按 code 做友好提示。

## 第二部分：模块 004 会话与消息

**范围**：创建会话、会话列表（倒序分页）、会话详情、历史消息分页、最近 N 轮历史读取、数据隔离。

### 1. 路由冲突：`/list` vs `/{session_id}`

- `GET /api/session/list` 与 `GET /api/session/{session_id}` 会撞路由，FastAPI 按注册顺序匹配。
- 解决：**先注册 `/list` 再注册 `/{session_id}`**，否则 `/list` 会被当成 session_id 解析失败。

### 2. 数据隔离：越权返回 404 而非 403

- 访问他人会话若返回 403 会**泄露会话存在性**。契约要求统一 `404 session_not_found`。
- 实现：`get_session_for_user(db, id, owner)` 按 `id + owner` 联合查询，查不到直接 404，与"不存在"无差别。

### 3. `(create_time, id)` 复合排序保证稳定分页

- 仅按 create_time 排序时，同毫秒插入的多条消息顺序不确定，翻页会出现重复/漏条。
- 解决：`ORDER BY create_time ASC, id ASC`，id 作为唯一决胜键。

### 4. 批量插入 create_time 相同的坑（测试侧）

- 同一事务内 `db.add()` 多条消息，`datetime.now()` 默认值在**同一次 flush** 求值，时间几乎相同 → 排序测试结果取决于 id。
- 教训：**排序类测试必须显式构造递增的时间戳**，否则断言不具确定性。

### 5. "N 轮" 与 "N 条" 的语义差异（spec 自身不一致）

- 规格文字说"携带最近 N 轮"，data-model 查询却写 `LIMIT N`（按**消息条数**）。两者对 `N=6` 语义差一倍。
- 决策：以 data-model 契约为准实现 `LIMIT N 条消息`，在 `services/history.py` 注释标明；后续如需严格按"轮"（N×2 条）改一处即可。

### 6. 标题自动摘要规则

- 创建时默认「新会话」，首条用户消息写入后若仍为默认标题，截取前 20 字符 + "…"。
- 仅在**仍为默认标题**时更新，用户/系统已改的标题不覆盖。

## 第三部分：模块 002 知识库

**范围**：上传校验、文本解析（编码兜底）、段落感知切分、Embedding 可插拔、Chroma 向量库封装、后台解析流水线、状态机（处理中/就绪/失败/已取消）、级联删除。

### 1. 后台任务的生命周期：请求会话 vs 独立会话

- 后台任务在**响应返回之后**（甚至另一个 worker 进程）才执行，此时请求级 `Session`（`Depends(get_db)`）早已关闭 → 直接复用必然抛 `DetachedInstanceError`。
- 解决：`pipeline.process_document(doc_id)` **自开 `SessionLocal()`**，与请求会话解耦。Celery 任务在独立进程由 worker 执行，请求依赖根本不存在，必须任务内自管 Session。这是后台任务模型（无论 BackgroundTasks 还是 Celery）的经典坑。

### 2. EphemeralClient 同进程共享数据 → 测试隔离失效（本次最隐蔽的坑）

- 想当然以为"测试用 `EphemeralClient`，每次 `reset_collection()` 把单例置 None 就干净了"。
- 实测：**同进程内多次 `chromadb.EphemeralClient()` 共享同一份底层存储**，新客户端会重新打开旧数据。置 None 后新客户端看到的仍是上一个测试写入的切片 → 断言 count 一直偏大。
- 解决：`reset_collection()` 先 `get()` 出全部 id 并 `delete()` 清空，再置 None。**教训：`with_variant` 解决数据库差异，但"进程内共享存储"这种隐式状态只能靠实测发现。**

### 3. Chroma 的 `where` 过滤（元数据检索）

- 删除/召回都依赖元数据过滤：`delete(where={"doc_id": doc_id})`、`query(where={"doc_id": {"$in": [...]}})`。
- 经验：where 等值写法 `{"field": value}` 即可（无需显式 `$eq`）；`$in` 用 `{"$in": [...]}`。过滤条件与存储类型（int）必须一致。

### 4. identity map 陷阱：`db.get` 返回陈旧对象

- 流水线在校验"文档是否被并发删除"时，用 `db.get(KnowledgeDoc, doc_id)` 复查。但该对象**本会话已加载**，identity map 直接命中缓存返回旧对象，永远不会是 None → 并发删除分支失效，甚至写 `UPDATE` 时抛 `StaleDataError`（0 行匹配）。
- 解决：复查必须 `db.get(..., populate_existing=True)` **强制回源 DB**；行已删则返回 None。
- 测试侧同坑：测试会话里验证"文档已删"时，`expire_all()` 后再 `get` 会抛 `ObjectDeletedError`（而非返回 None），需用**全新 Session** 查询。

### 5. 整份失败回滚（FR-011）

- 批量向量化中途失败（如第 2 批 embedding 超时），前 16 个切片已写进 Chroma → 不能留半成品。
- 基础解决：`except` 分支统一 `chroma.delete_by_doc_id(doc_id)` 回滚全部切片，文档/任务状态置失败。测试用"第二次 embed 抛错"的 Flaky 客户端验证。
- **增强一：删除操作自身异常单独捕获**。`chroma.delete_by_doc_id` 增加 `raise_on_error` 参数：普通清理路径默认吞掉（Chroma 无匹配元数据会抛空 where 错误），FR-011 回滚路径传 `raise_on_error=True`，由 pipeline 的 `_rollback_chunks` **再次 try/except 捕获删除异常并输出 ERROR 告警**（向量残留 = 半成品，必须可观测）。**无论删除成功与否，MySQL 文档/任务状态都必须置为失败**——把「标记失败」从删除结果的从属位置中剥离，保证状态机收敛。
- **风险说明：进程崩溃 / OOM 不会进入 except 分支**。整份回滚只覆盖「能捕获的异常」；进程被强杀 / OOM 时任务还停在「处理中」，没有任何代码执行 → 僵尸任务。兜底方案分两层：
  1. **已实现：启动清扫**。应用启动时调用 `mark_stale_processing_timeout()`，把上次进程遗留的超时「处理中」任务/文档置失败（SC-004 防卡死）。单进程 dev 场景下，重启即意味前一个解释器已死，遗留的「处理中」必然是僵尸。
  2. **运行期周期清扫（2026-08-31 已落地方案）**。在 `main.py` lifespan 内用 `asyncio.create_task` 启动内部循环，`await asyncio.sleep(parse_timeout_seconds)` 后周期调用 `mark_stale_processing_timeout()`，处理「进程长期存活期间的崩溃」；随应用启动/停止，无需 APScheduler / celery beat / 外部常驻进程（见 specs/002-knowledge-base/research.md §1）。
- **增强二：Embedding 批次有限重试**。`embed_texts` 对每个批次做**有限重试**（`embedding_retry_times=2`，线性退避 `embedding_retry_backoff_seconds`），只重试 `LLMError`（网络超时/连接中断等瞬时故障）；重试耗尽仍失败才走整份回滚，避免一次瞬时抖动就整份失败。
- **增强三：重复触发防护（防并发竞态）**。`process_document` 入口增加守卫：文档状态为「处理中」且**已存在进行中的 ParseTask** 时，拒绝再次触发并打 warning 返回。判据必须落在「进行中任务」而非文档状态本身——首次上传触发时文档也是「处理中」，但尚无 ParseTask，不能误拦；而重复触发（任务排队/重复调度）会看到已存在的进行中任务而被拒。

### 6. 级联删除的外键约束（MySQL 会 500）

- `cleaner` 删除文档时若 ParseTask 仍存在，MySQL 默认 `RESTRICT` 外键会直接拒绝 DELETE → 接口 500。
- 解决：模型与 init.sql 的 FK 均加 `ON DELETE CASCADE`，且 cleaner 显式 `delete(ParseTask)` 一并清理（SQLite 默认不启用 FK 级联，靠显式删除保证行为一致）。

### 7. 编码兜底（中文现实问题）

- 上传的 txt/md 可能是 UTF-8、带 BOM 的 UTF-8、或 GBK。单个 `decode("utf-8")` 遇到 GBK 直接抛错。
- 解决：按 `utf-8-sig → utf-8 → gbk` 依次尝试，全部失败才报 `parse_error`。
- Windows 额外坑：`Path.write_text` 文本模式会把 `\n` 写成 `\r\n`，解析结果带 `\r` 导致断言不一致 → 测试显式 `newline="\n"`。

### 8. Embedding 后端可插拔设计

- 本机未装 Ollama，若硬耦合 `httpx.post(".../api/embed")` 则**测试全部跑不了**。
- 解决：`EmbeddingClient` 抽象 + `get_embedding_client()` 工厂（ollama / local / **openai_compat** 三后端）。运行默认 `openai_compat`（SiliconFlow 免费 bge-m3）：本机内存紧张（提交常近上限），本地加载 bge-m3 会 OOM/Ollama 502；云端零本地内存。测试用 `autouse` 夹具 monkeypatch 成 `FakeEmbeddingClient`（token 哈希确定性向量，同一 token 余弦≈1，检索断言可复现）。

## 第四部分：模块 001 RAG 流式问答

**范围**：长度/配额校验、最近 N 轮历史、向量检索（阈值过滤+top-k）、Prompt 组装与预算截断、LLM 流式、SSE 事件协议（meta/data/finish/error）、空检索兜底、消息持久化、输出后来源校验。

### 1. StreamingResponse 的生命周期：body 生成器晚于请求会话

- FastAPI 端点返回 `StreamingResponse` 时，**body 生成器在响应返回之后才逐段执行**，此时 `Depends(get_db)` 的请求级会话已关闭 → 在生成器里写库必然抛 `DetachedInstanceError`。
- 解决：生成器内自开 `SessionLocal()`（与 002 pipeline 同理）。前置校验（长度/配额/会话归属/检索）仍在端点内用请求会话同步完成，只有流式中的持久化换独立会话。

### 2. schema 校验 vs 业务校验：谁先返回

- 一开始 `ChatRequest.question` 加了 `Field(max_length=500)`，501 字问题被 Pydantic 在路由层拦成 **422**，`validate_question` 永远轮不到 → 违反契约要求的 400 `question_too_long`。
- 解决：schema 层只保留类型，**空/超长交给业务层**统一转契约错误码。教训：带自定义错误码的校验不要和 Pydantic 默认校验抢位置。

### 3. 伪 embedding 的相似度语义：阈值与向量绑定

- 测试用 token 哈希稀疏向量模拟 embedding，踩了两个坑：
  - **整段 CJK 一个 token**：「退货政策」≠「退货」，语义近但字面不重叠就余弦为 0 → 测试文档文本必须**逐字包含**问题短语。
  - **稀疏向量余弦被摊薄**：文档 token 越多，命中 query token 的余弦 ≈ `1/√n`，0.55 阈值（bge-m3 稠密向量的校准基线）过不去。
- 解决：测试文档文本刻意包含问题短语 + 集成测试放宽阈值到 0.1（注释说明原因）。**要点：相似度阈值不是绝对常量，是与具体 embedding 绑定的校准参数**；换 embedding 必须重校准。

### 4. Chroma cosine 距离与相似度阈值的换算

- Chroma collection 用 `cosine` 空间，返回的是 **distance = 1 - 相似度**。配置项 `rag_similarity_threshold=0.55` 是相似度 → 过滤条件写成 `distance <= 1 - 0.55`，直接拿 0.55 当距离阈值会过滤掉所有命中。

### 5. async generator vs 协程函数（测试假 LLM 的坑）

- `async def boom(messages): raise X` **没有 yield 就是协程函数**，返回 coroutine 而非 async generator；`async for` 无法迭代它，异常绕开内层 try 落到外层 `except Exception` → 错误码变成 `llm_error` 而非 `llm_timeout`。
- 解决：函数体内补一个不可达 `yield`，使其成为真正的 async generator，异常在首个 `__anext__` 触发并被正确捕获。

### 6. 配额原子递增（并发不重复计数）

- 规格要求校验+递增同事务：`UPDATE ... SET count = count + 1 WHERE count < :limit` 单语句原子；`rowcount==1` 说明消费成功；`rowcount==0` 分两种情况——当日无记录则 INSERT（count=1），否则已达上限抛 429。首条提问走 INSERT 分支。

### 7. SSE 事件序列约束的测试断言

- `meta` 至多一次且在首个 `data` 前；`finish`/`error` 互斥且为最后一个事件；`error` 后不得再发 `data`。
- 空检索兜底：**不建立 LLM 连接**，用带计数器的假 stream 断言 `called == 0`。
- error 分支也要持久化 AI 消息（内容为错误文案），保证「不发空响应、不静默结束」。

### 8. 上下文超长截断的降级顺序（FR-011）

- 预算 = `context_max_tokens × 1.5 字符/token`。超限时**先按消息边界丢最早历史**，仍超再**从末尾减知识片段**（保持编号连续），严禁先丢知识。
- 测试陷阱：`max_tokens=200` 预算 300 token，但 System Prompt+知识+问题只有约 212 token → 根本不触发截断。设计截断测试前先算清字符量级。

## 第五部分：模块 001 混合检索（向量 + BM25 + RRF）与 Reranker 精排

**范围**：把 RAG 检索从「单路向量」升级为「向量 + BM25 双路召回 → RRF 融合 → Reranker 精排」；jieba 分词 + 自研 Okapi BM25、显著词闸门、可插拔降级的精排器。

### 1. jieba 依赖 + 自研 Okapi BM25（不引 jieba_bm25 的原因）

- 决策：jieba 只负责**中文分词**；BM25 打分（k1=1.5、b=0.75 的 Okapi 公式）在 `bm25.py` **自研**。
- 原因：宪法要求「核心链路自研可读」。第三方 `jieba_bm25` 是黑盒打分包，内部具体实现不可控；而 Okapi BM25 公式是公开标准，几十行即可实现，可解释、可调参、可单测。
- 实现要点：`tokenize` 先抽 ASCII 单词（`[A-Za-z0-9]+`，len≥2 小写），剩余文本交 `jieba.lcut` 取含 CJK 的 token；jieba 导入失败 → `JIEBA_AVAILABLE=False`，退化只留 ASCII，不崩溃。
- Python 3.14 下 jieba 是纯 Python 包，有轮子可直接 `pip install jieba`（0.42.1 实测可装）。

### 2. 空检索兜底的边界坑：朴素字符分词假阳性 → 显著词闸门

- 症状：`test_empty_retrieval_fallback_without_llm` 问「今天的天气怎么样」，应走兜底（不调 LLM）；朴素切分（按字符/单字）会让该问句因共享「的/天/么」命中「退货政策」文档 → 假阳性破坏兜底语义。
- 本质：**功能字不能作为关键词召回的信号**。单字「的/了/天/么」在几乎每个中文句子里都出现，DF 极高、区分度≈0。
- 解决：**显著词闸门（`passes_gate`）**——候选片段必须与问题共享 ≥1 个**显著词**（CJK 二元及以上词，或 ASCII 单词 len≥2）才进入打分。闸门通过后，一元 token 仍参与打分（不浪费信息）。
- 教训：关键词检索的「相关性」必须先于「打分」用闸门圈定，否则打分再准也会被高频功能字污染。

### 3. RRF 融合：基于排名而非分数，天然免尺度对齐

- `RRF(doc) = Σ 1/(k + rank)`，`k=60`（`rag_rrf_k`）。两路各按名次贡献分，两路都命中的 doc 拿两项 → 自动排到单路命中之前。
- 关键收益：向量余弦分与 BM25 分**量纲不同、无法直接相加**，RRF 只用排名，免去分数归一化对齐。双路并集 + 名次分 → 粗筛候选池 `rag_candidate_k=20`，为精排留足候选。
- 参数：`k` 越大两路权重越平均；60 是 BM25/RRF 融合的常见经验值（0.5 * top-K 数量级内稳定）。

### 4. Reranker 可插拔 + 全链路降级（未装模型也能跑）

- 抽象：`Reranker` 协议 `rerank(query, texts) -> list[float]`（与 texts 等长，越大越相关）。
- `CrossEncoderReranker`：**懒加载**——构造不 `import sentence_transformers`，首次 `rerank` 才 `_load()`，避免无模型环境在导入期就崩。
- `NoopReranker`：返回递减整数 → 降序排序保持原序（等价于「不重排」）。
- 决议链（`get_reranker()`，进程级缓存）：`rag_reranker_enabled=False` → Noop；`importlib.util.find_spec("sentence_transformers") is None`（未安装，用 find_spec 而非 try-import，因为 import 会有延迟/副作用）→ Noop；否则 CrossEncoder。
- 降级链：`warmup()`（应用启动 best-effort，失败吞异常置 Noop）→ `retriever` 精排段 try/except（推理异常回落 RRF 融合序，日志 warning）。**任何一环失败都不影响主链路**。
- 测试隔离：`reset_reranker()` 清进程缓存；单测用 `monkeypatch` `find_spec` / 注入假 `sys.modules["sentence_transformers"]` / 注入假精排器控制行为，不依赖真实模型。

### 5. sentence-transformers + torch + bge-reranker-v2-m3 镜像安装教程

> 本沙箱 **不预装** 精排模型依赖（torch 包体大），需要精排能力时按本节自行安装。未安装时服务自动降级，不影响验收主链路。

```bash
cd backend

# ① 国内 PyPI 镜像装 sentence-transformers（会自动拉 torch，改用镜像源加速）
.venv/Scripts/pip install sentence-transformers -i https://pypi.tuna.tsinghua.edu.cn/simple
# 备选：阿里云镜像  -i https://mirrors.aliyun.com/pypi/simple/

# ② torch 单独装 CPU 版（如上面自动拉的是带 CUDA 的过重包）
# 查看当前 torch：.venv/Scripts/pip show torch
# 需要重装 CPU 版（仅 200MB 级）：
.venv/Scripts/pip install torch --index-url https://download.pytorch.org/whl/cpu
```

**模型权重下载（HF 被墙时的三选一）**：

```bash
# 方案 A：hf-mirror.com 环境变量（最省事，sentence-transformers 自动识别）
export HF_ENDPOINT=https://hf-mirror.com
# Windows PowerShell：$env:HF_ENDPOINT = "https://hf-mirror.com"
.venv/Scripts/python -c "from sentence_transformers import CrossEncoder; m=CrossEncoder('BAAI/bge-reranker-v2-m3'); print('ok', m)"  # 触发下载到缓存

# 方案 B：ModelScope（国内源，模型同名，改名即可）→ 下载后设本地路径加载
#   网页：https://www.modelscope.cn/models/BAAI/bge-reranker-v2-m3
.venv/Scripts/pip install modelscope -i https://pypi.tuna.tsinghua.edu.cn/simple
.venv/Scripts/python -c "from modelscope import snapshot_download; print(snapshot_download('BAAI/bge-reranker-v2-m3'))"

# 方案 C：先下权重到本地目录，改配置指向本地路径
#   .env: RAG_RERANKER_MODEL=D:/models/bge-reranker-v2-m3
#   要求该目录含 config.json + pytorch_model.bin 等完整权重文件
```

**安装后验证**：启动后端，日志应出现一次 `warmup_reranker` 成功（无降级 warning）；提问时 `meta` 顺序为精排序。未安装时日志出现一次「Reranker 未安装/降级」warning 且链路正常。
