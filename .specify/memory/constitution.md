# Nexus 智能客服系统宪法 (Nexus Support Agent Constitution)

本宪法约束本项目（基于 LLM + RAG 的企业级智能客服系统）的全部设计与实现。
本系统覆盖：用户会话管理、知识库文档解析与向量化存储、向量检索、
Prompt 组装、大模型调用、SSE 流式回答、答案来源引用、用户反馈统计；
支持多轮对话，并对检索为空、LLM 超时、限流、上下文超长、幻觉等工程问题做处理。

## Core Principles

### 一、RAG 核心链路必须可读可控（NON-NEGOTIABLE）

向量切分、Embedding、检索、Prompt 组装的**核心逻辑必须自研可读，其他部分无需自研**。
禁止直接调用高阶封装链（如未理解内部逻辑的黑盒 LangChain 链）；
必须允许手动实现核心链路，以便调优、排错和验证效果。
可借助辅助库，但任何一层必须能被项目成员解释其原理。

**理由**：RAG 质量依赖对每一环节的精确控制；黑盒链路导致幻觉与
检索问题无法定位，也违背系统"可解释、可审计"的要求。

### 二、禁止编造与幻觉抑制（NON-NEGOTIABLE）

- 检索无有效片段时**必须**输出固定兜底话术
  （`抱歉，知识库中没有找到相关信息，请换个方式提问或者联系人工客服。`），
  禁止模型编造内容。
- 每次 AI 回答**必须**附带引用来源：文档名称 + 片段摘要。
- System Prompt 必须强约束：仅基于提供的知识库内容回答；知识库无信息不得编造。
- 输出后**必须**做来源后校验：检出内容超出知识库范围的，标记提示而非静默放行。

**理由**：客服场景中错误信息直接损害用户信任；来源引用是防幻觉的
最小可信边界，也是可测试的验收标准。

### 三、AI 能力仅在服务端执行

- LLM 调用与向量检索**必须**全部在后端完成；
  前端**禁止**直接调用大模型 API。
- 所有模型、密钥、配置仅存在于服务端环境；
  前端只能通过 REST API 与 SSE 流与后端交互。

**理由**：密钥与调用成本不能暴露给客户端；只有服务端才能施加
限流、审计与提示词约束，保证一致性与安全。

### 四、流式输出与耗时任务异步化

- 回答**必须**以 SSE 流式返回，禁止全部生成完成后再返回。
- SSE 事件协议统一为：`data`（token）、`meta`（引用来源）、
  `finish`（结束）、`error`（错误）四种事件。
- 文档解析与向量化是耗时操作，**必须**后台异步执行（BackgroundTasks /
  Celery）；HTTP 接口先返回，数据库以状态机记录
  `处理中 / 就绪 / 失败`。

**理由**：流式输出是业务硬性要求，避免用户长时间空等；
异步化防止耗时任务阻塞接口、拖垮系统。

### 五、硬性业务约束（NON-NEGOTIABLE）

- 单条用户提问最大长度：**500 字**，超长必须拒绝并提示。
- 用户每日提问次数上限：**可配置，默认 100 次 / 用户 / 天**，
  超限必须返回错误。
- 所有第三方 API 密钥**必须**使用环境变量配置（提供 `.env.example`），
  禁止硬编码；真实密钥禁止提交仓库。
- 删除知识库文档**必须**同步删除对应向量库切片数据（依 `doc_id` 级联）。
- 多轮对话**必须**携带最近 N 轮历史（N 可配置）；上下文超长时
  **必须**执行截断策略（优先截断最早历史、保留并压缩知识片段）。

**理由**：上述为题目与产品层面的硬性边界，违反即视为不合规实现，
直接影响交付验收。

## 安全与合规

- 认证：注册 / 登录（手机号或邮箱 + 密码），采用 **JWT** 鉴权；
  受保护接口必须校验 JWT，未鉴权请求一律拒绝。
- 密码明文化存储（哈希），禁止明文落库。
- 密钥与配置：仅存于服务端环境变量；`.env.example` 提供结构模板，
  真实密钥不得提交仓库。
- 用户消息、反馈数据仅用于系统功能；管理后台的数据查询与统计
  必须经过鉴权授权。
- 向量库内部 ID 与 MySQL 知识库文档 ID 建立关联，构成可追溯的索引对。

## 开发流程与质量门槛

- **测试优先（TDD）**：先写测试、再实现，遵循红-绿-重构循环。
- **关键链路集成测试（必须）**：文档解析→向量化入库、
  完整 RAG 问答链路、SSE 事件协议、文档删除级联。
- **工程问题必须实测覆盖**：检索为空、上下文超长截断、
  LLM 超时 / API 限流（429）异常捕获、幻觉后校验。
- 本地方案以 MySQL 8.0 + Chroma + bge-m3（Embedding，Ollama 提供）+ DeepSeek V4 Flash（LLM，OpenAI 兼容 API）可沙箱运行；
  切换生产组件（对象存储、向量库、LLM 服务）必须提供迁移方案。
- 项目提交文档必须包含：技术选型理由、RAG 架构图、
  工程问题处理说明、AI 编程工具使用说明。



### 闭环验证（Spec → Code 完整性检查）

测试通过 ≠ 一定正确。每次交付 MUST 完成三轮验证：

**第一轮：Spec → Code 映射表**

逐条核对 Spec 每条要求映射到对应代码位置，形成映射表（Spec 要求 / 代码位置 /
是否实现）。存在未实现的条目时，MUST 交由 AI 补全后再进入下一轮。

**第二轮：运行测试验证**

运行全部测试（如 `pytest tests/ -v`），预期全部 PASSED。存在失败时 MUST：
将失败信息（文件、行号、失败原因）交给 AI 修复 → 重新运行 → 直到全部通过。

**第三轮：人工审查（最终质量关卡）**

AI 生成 + 测试通过 ≈ 90% 正确率，剩余约 10% MUST 依赖人工审查。审查清单：

- 安全边界: 敏感数据泄露（API Key、个人信息出现在日志或返回值）、SQL 注入 / XSS、
  幂等性（同一请求多次发送的结果）
- 性能: N+1 查询（循环内反复查库）、无限递归（Agent 无限循环）、内存泄漏
- 用户体验: 错误信息是否友好、边界情况反馈是否清晰
- 可维护性: 命名是否清晰、是否有不必要的复杂度、注释解释「为什么」而非「是什么」

### 人工介入提示 (Human Intervention Prompts)

需要人工介入的环节 MUST 及时提示用户，不得静默跳过或由 AI 自行替代：

- 编写测试用例（正确性由人定义）
- 第三轮人工审查（安全/性能/UX/可维护性以人工为准）
- Spec 与测试冲突、需要修改 Spec 等决策点（遵循「歧义与冲突先提问」规则）

## AI 协作行为准则 (AI Collaboration Rules)

- **技能调用报告**: AI 助手在每次返回结果给用户时，MUST 准确报告本次执行中调用过的
  全部 skills（如 speckit-constitution、speckit-specify、speckit-tasks 等），并简要
  说明每个 skill 的用途。
  **理由**: 保证工作流透明可审计，让用户能追踪每个步骤的执行来源，便于复现与质量核查。
- **歧义与冲突先提问**: 当指令存在歧义、信息缺失或需求之间互相冲突时，AI 助手
  MUST NOT 自行随意选择一个解释或方案执行，而必须先向用户提问，明确指出歧义/冲突点，
  并给出多个互斥的候选选项（可附推荐项与理由），在用户做出选择后才继续执行。该规则
  适用于所有影响方向或产出的决策，尤其是不可逆或高成本操作。
  **理由**: 避免误解需求导致返工与资源浪费，把决策权始终保留给用户。
- **阶段性总结与验证 (Milestone Summary & Verification)**: 写代码/实现过程中，每完成
  一个可独立提交 git 的目标（里程碑）时，MUST 停止继续推进并：
  - 总结本次完成的内容（做了什么、涉及哪些文件/功能）
  - 总结本次的重点和难点（实现功能的过程中的难点，踩过的坑，面试可能会问的点）
  - 给出一个可执行的验证方法（如运行某命令、执行某测试、访问某页面/接口）
  - 结束当前工作，等待用户验证并确认后再继续下一个目标
  **理由**: 小步快跑、每步可验证，避免大段改动难以审查，让用户全程掌握进度并及时纠正。
- **回复和输出内容都使用中文**
- **如果写代码时方案要求的环境未配置，自主配置，遇到需要人手动安装的向用户说明**

## Governance

本宪法**高于**其他任何项目实践与个人偏好；所有实现必须服从本宪法。

修订程序：任何修改须由参与者提出修订说明（修改内容与原因）、
经确认通过后落地，并在本文档更新版本号与修订日期。
修订历史不得删除旧版关键条款，重大变更需评估迁移影响。

版本策略：MAJOR 为治理或原则的破坏性移除 / 重定义；
MINOR 为新增原则或章节、实质性扩充指导；
PATCH 为澄清措辞、错别字、非语义精修。

合规评审：每次变更交付 / 合并前，必须对照本宪法逐条核验；
不能解释的偏差需正当化并经评审确认；复杂度必须被理由支撑。
