# 研究记录：意图识别（三层漏斗）

**日期**：2026-08-29 | **特性**：[spec.md](spec.md)

本文件记录 Phase 0 对技术上下文 unknowns / 依赖 / 集成的研究结论，统一为「决策 / 理由 / 备选方案」。

## 1. AC 自动机关键词匹配：选用 ahocorasick-ng（不自研）

- **决策**：**采用 `ahocorasick-ng` 库**实现关键词集合匹配（用户明确指定，不自研）。关键词经文本归一化后按「词 → 意图」写入自动机；匹配使用**最长匹配模式**（`iter_long` 语义，多条命中取更长者）；**词边界校验在库命中基础上做薄封装**——库返回命中位置（start/end），在命中串前后各取一个字符校验是否词边界字符，实现「只匹配完整语义片段」。
- **理由**：ahocorasick-ng 是 pyahocorasick 的维护继任者（Cython 加速、API 兼容家族：`Automaton` / `add_word` / `make_automaton` / `iter` / `iter_long`），对几百到几千中文关键词量级性能与内存绰绰有余；天然支持多模式串同时匹配与最长匹配，正是 FR-002 所需。词边界是该类库的共性空白（按字符粒度匹配、无语言词法概念），需薄封装补上，但这层逻辑简单可测，不影响「读得懂、控得住」。
- **宪法说明**：宪法原则一「核心链路必须自研可读」明示的清单是 RAG 链路的切分/Embedding/检索/Prompt 组装；本特性为问答链路前置的辅助匹配组件，选用成熟、原理清晰（goto/failure/output 三表结构）且团队可解释的算法库，不属于「未理解内部逻辑的黑盒高阶链」范畴，故不构成原则一违规。实施时以仓库锁定版本为准核对其确切 API 名（iter_long 与词边界封装）。
- **备选方案**：自研 AC 自动机（已被用户明确否决，改库方案）；pyahocorasick（已被 ahocorasick-ng 继任，选 ng 版）；朴素逐关键词 `in` 扫描（关键词多时退化为 O(N×L)，无失败指针复用，不满足多模式串同时匹配要求）。
- **2026-08-30 落地更新**：实测 `ahocorasick-ng` 在 **Python 3.14 / Windows 下无任何可用发行版**（`pip install` 报 `No matching distribution found`，连 sdist 都没有）→ 落地改用其**同 API 上游包 `pyahocorasick` 2.3.1**（有 `cp314-win_amd64` 轮子，实测安装成功，导入名同为 `ahocorasick`）。匹配逻辑（`Automaton` / `add_word` / `make_automaton` / `iter` / `iter_long`）与词边界薄封装完全不受影响。

## 2. 句式模板匹配：选用 pyparsing（不自研）

- **决策**：**采用 `pyparsing` 库**定义句式模板语法（用户明确指定，不自研）。用声明式文法表达固定句式，如「帮我查询 + 任意内容」→ 产品咨询、「取消订单 + 订单号」→ 售后；模板携带意图标签与**命名结果**（named results），模板表存配置文件（YAML/JSON），加载时编译为 pyparsing 解析器。
- **理由**：FR-004 要求识别"帮我查询X / 取消订单X"这类**强固定句式**；pyparsing 是成熟通用的声明式解析库，文法可读、支持命名捕获与组合，比正则更适合表达「前缀 / 槽位 / 可选片段」这类模板结构。规则层只兜强固定句式（用户设计明确：改写/倒装交给小模型），模板量级小、维护清晰、命中即短路。
- **备选方案**：正则 DFA 模板（自研正则方案，已被用户明确否决，改 pyparsing）；通用 NLU 库（Rasa/spaCy 规则组件）→ 引入重依赖、黑盒化；自研完整解析器 → 对固定句式过度设计。

## 3. 文本归一化（规则层前置）

- **决策**：自研 `normalize.py` 归一化流水线：全角→半角、去空白与特殊符号 → 繁简转换（轻量映射表，v1 用内置常用字表，避免引入 opencc 重依赖）→ 常见形近字纠错（配置化纠错表，如"退还/退货"归一）。归一化结果仅用于规则层匹配，原始输入保留入库展示。
- **理由**：FR-001 要求规则层命中率不因全角、繁体、乱入符号而下降；零模型成本换规则层覆盖面。形近字纠错表按业务高频错别字维护，避免通用纠错库的误伤。
- **备选方案**：opencc 做繁简（功能全但体积大，繁简场景低频，先用内置常用字表）；直接不归一化（繁体"投訴"/全角标点导致规则漏配，违背用户"输入情况多样"的约束）。

## 4. 小模型置信度获取与双阈值（核心工程决策）

- **决策**：小模型（DeepSeek-R1-0528-Qwen3-8B）按「意图 + 置信度」JSON 结构化输出；置信度采用**两段式策略**：
  1. **JSON 自报置信度（默认主力）**：模型在 JSON 中输出 `confidence`（0~1），配合严格 system prompt 约束；
  2. **临界带二次采样（可选增强）**：仅当自报置信度落在【低阈值，高阈值）临界带时，同 prompt 低温采样投票 N=3~5 次，用**投票一致率**作为二次置信度复核，一致率不足则视为低置信度流转下一层。把「采样多次」的昂贵成本只花在真正模糊的少数样本上。
  - 双阈值默认：`high_threshold=0.9`、`low_threshold=0.6`（经标注集校准可调）；若部署端点不支持可调采样参数，则退化为自报置信度 + 反向校准（§5）双兜底。
- **理由**：FR-008 双阈值判定依赖数值化置信度；目标模型为 R1 推理蒸馏变体，**官方 API 明确不支持 logprobs**（见 §6），而自建/第三方端点的 logprobs 暴露因框架而异、不可作为通用前提——故模型自报置信度是成本最低的可用信号，临界带二次采样弥补其「校准差、易过度自信」的缺陷；反向校准再从另一维度兜住误判。阈值默认值取 0.9/0.6 是「高阈值宁缺毋滥、低阈值宁流转大模型也不硬猜」的取向，与用户「尽量不采信低置信度结果」的目标一致。
- **备选方案**：logprobs 概率（R1 系列 API 不支持，不可用，见 §6）；正则抽取模型回复关键词做启发式置信度（脆弱）；全量多次采样投票（成本 ×N，仅限临界带触发以控成本）。

## 5. 反向校准（负样本校验）实现

- **决策**：反向校验采用**特征规则通道为主、模型自评通道可选**的双通道设计：
  - **特征规则通道（默认）**：为每个意图维护一组「反特征」负样本库（词/正则，配置化）。模型输出意图 A 后，对归一化输入做 A 的负样本匹配，命中即拒绝该预测（防"投诉咨询中心"这类把强咨询误标为投诉）。
  - **模型自评通道（可选开关）**：向小模型二次提问「该输入是否真正属于意图 A 的特征？」，输出是/否+原因；结果"否"即拒绝。该通道多一次模型调用，默认关闭，仅对高价值或调试场景开启。
- **理由**：FR-007 要求「不采信不符合意图特征的输出，抑制小模型幻觉与乱打标签」。特征规则通道零额外模型成本、确定可测，作为主力；模型自评通道提供语义级兜底但增本，按需开启。用户设计强调反向校准是「抑制小模型幻觉、防止把模糊问句强行分类」的关键，故作为独立决策点。
- **备选方案**：仅模型自评（增本 + 二次调用的幻觉叠叠乐）；仅规则负样本（覆盖不了语义级误判，可接受为 v1 基线）。

## 6. 模型 API 形态（DeepSeek 调用方式）——外部事实（已核查）

> 结论已与实现解耦：客户端统一走 OpenAI 兼容协议，`base_url` / `api_key` / `model` 全部可配置，模型名与协议变更不影响主链路。

- **决策**：客户端按 **OpenAI 兼容协议**实现（`httpx` 直连 `POST /chat/completions`，Bearer 鉴权，薄客户端），统一封装 `small_model/client.py` 与 `fallback/client.py`，仅模型名与参数不同。结构化输出使用 `response_format={"type":"json_object"}`，**返回 schema 在客户端自行校验**（字段存在/类型/枚举值），不依赖服务端强约束。客户端显式设置超时（默认 30~60s）并对 429 做指数退避重试。
- **理由**（外部核查结论）：
  1. DeepSeek 官方 API（`api.deepseek.com`）完全兼容 OpenAI 协议，但**仅支持 `json_object`、不支持 OpenAI 的 `json_schema`**——schema 必须客户端自验；
  2. **`DeepSeek-R1-0528-Qwen3-8B` 并非官方 API 的 model ID**（官方只有 `deepseek-chat` / `deepseek-reasoner`），它是 DeepSeek 开源发布的「R1-0528 蒸馏到 Qwen3-8B」权重，只能经**本地部署（vLLM/Ollama）或第三方平台（如 OpenRouter）**访问——与本特性「小模型经 HTTP API 调用、密钥占位」的设计完全吻合，且该端点的 logprobs/json_object 兼容性因推理框架而异，故客户端要**薄、可配置**，不能假设支持官方全部参数；
  3. `logprobs/top_logprobs` 在官方文档存在但对 **R1/reasoner 系列不可用**，故置信度方案不依赖 logprobs（见 §4）；
  4. 官方未公开统一默认超时与严格 RPM/TPM 配额，超时与重试须客户端显式处理。
- **备选方案**：openai SDK（简化调用但引入 SDK 依赖，且对非官方端点的兼容性细节封装不透明）；厂商专属 SDK（锁定，违背可迁移性）。

## 6.1 成本统计（usage 落库）

- **决策**：模型客户端每次调用后记录 `usage`（`prompt_tokens` / `completion_tokens` / `total_tokens`，含 `reasoning_tokens`）连同 model、时间戳、所属漏斗层级（small_model/fallback）写入日志/统计表；成本按 token 数 × 费率自算（DeepSeek 响应不含 cost 字段，费率不硬编码）。
- **理由**：三层漏斗的核心目标即算力成本优化，需要可观测的**各层调用占比与 token 成本分摊**来验证「规则层拦截省了多少」；R1 系推理模型的 `reasoning_tokens`（thinking）会让单次 completion 成本放大数倍到数十倍，是成本观测的关键指标，也支撑反向校准模型自评通道默认关闭的决策。
- **备选方案**：不统计（无法量化三层漏斗的经济性收益，违背本特性价值目标）；依赖平台侧 cost 字段（OpenRouter 有、DeepSeek 原生无，不可通用）。

## 7. 大模型兜底 Few-shot 设计

- **决策**：`fallback/` 模块组装兜底 prompt：系统指令（你是意图识别器，只输出 JSON）→ 可用意图清单（四类 + 未识别）→ 4~6 组 Few-shot 样例（覆盖每类意图至少 1 例 + 1 例歧义归"未识别"）→ 用户 query。强制 `response_format`（JSON 结构化）或解析失败走降级；解析失败/超时/429 统一降级为「未识别 + 默认路由」。
- **理由**：FR-009/FR-010 要求 Few-shot 传达意图与输出格式、强制 JSON 可解析。样例覆盖每类意图保证少样本下分类稳定；歧义样例训练模型「不确定就标未识别」，抑制强行分类。
- **备选方案**：零样本直接分类（模糊输入更易乱标）；让大模型自由文本回复（违反 FR-010 强制 JSON）。

## 8. 路由分发与 001 集成点

- **决策**：`router.py` 维护 `intent → handler` 映射：产品咨询/售后 → `rag_qa` handler（依赖 001 特性，注入调用点）；闲聊 → `small_talk` handler（模板/轻量回复，不检索）；投诉 → `complaint` handler（转人工提示 + 留档）；未识别 → `default`（走 001 正常问答或兜底话术）。**集成点**：在 001 问答链路「输入校验之后、Query 向量化之前」插入 `recognize()` 调用，识别结果决定是否进入检索；通过依赖注入接入，不修改 001 主链路代码。
- **理由**：FR-012 要求按意图路由。闲聊/投诉不检索知识库是路由行为正确性的硬验收（SC-007）；「标注+路由分发」功能定位下，router 是意图结果的下游消费者统一出口；依赖注入保证 001/006 解耦，符合宪法「主链路可读可控」。
- **备选方案**：在 001 内部硬编码意图判断（污染主链路、耦合）；意图结果仅标注不路由（用户已确认要路由分发）。

## 9. 配置体系（密钥占位与阈值）

- **决策**：密钥类敏感配置走 `.env`。小模型层用**独立凭据** `SMALL_MODEL_NAME`/`SMALL_MODEL_API_KEY`/`SMALL_MODEL_BASE_URL`（可指向第三方/自建端点，不复用 DeepSeek）；兜底层复用 `DEEPSEEK_API_KEY`/`DEEPSEEK_BASE_URL` + `DEEPSEEK_LARGE_MODEL`。`.env.example` 提供占位模板，真实密钥不提交仓库；非敏感参数（双阈值、词库/模板/负样本文件路径、澄清重试次数）走 `system_config` 表 + 配置文件。
- **理由**：FR-014 要求模型密钥经环境变量、禁止硬编码；词库/模板/负样本是运营可调数据，落配置文件便于迭代维护，双阈值等运行时参数落 `system_config` 便于热调。
- **备选方案**：全部落 `.env`（词库这类长文本不适合环境变量）；全部落数据库（密钥与运维配置混存，不利于本地开发快速起步）。

## 10. 测试策略

- **决策**：pytest。单元测试：关键词匹配（ahocorasick-ng 最长匹配/词边界薄封装）、句式模板（pyparsing 文法命中与命名结果）、归一化（繁简/形近/全角）、双阈值判定、反向校准负样本；集成测试：三层漏斗全链路（mock 小/大模型 API，用真实输入验证"规则层不调模型""中段澄清""低置信度流转""兜底 JSON 解析"四条路径）、闲聊不检索路由断言、密钥未配置降级。
- **理由**：宪法「关键链路集成测试必须」「工程问题必须实测覆盖」；意图识别正确性依赖规则与阈值的组合，用可注入的 mock 模型保证各路径确定可复现，避免真实 API 波动。
- **备选方案**：仅真 API 测试（慢、贵、不可重复）；仅单元测试（无法验证三层编排与路由）。
