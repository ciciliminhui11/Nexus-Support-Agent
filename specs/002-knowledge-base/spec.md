# 功能规格说明：知识库管理

**功能分支**：`002-knowledge-base`

**创建日期**：2026-08-29

**状态**：草稿

**输入**：用户描述："知识库：文档上传、文档解析、向量化入库、知识库列表（状态：处理中 / 就绪 / 失败）、文档删除"

## 用户场景与测试 *(必填)*

### 用户故事 1 - 上传文档并异步完成入库（优先级：P1）

管理员上传一份知识库文档，接口立即返回成功，系统在后台完成解析、切分、向量化并写入知识库，文档最终变为「就绪」状态，可被问答链路检索命中。

**优先级理由**：这是知识库的核心价值 —— 让文档进入可检索的知识库。没有它就绪，RAG 问答无法命中任何内容，故为 P1。

**独立测试**：上传一份合法 txt 文档，可独立验证：接口即时返回、文档状态由「处理中」变为「就绪」、就绪后问答链路可命中该文档内容。

**验收场景**：

1. **假如** 管理员上传一份 txt 或 markdown 文档，**当** 提交上传，**那么** 接口立即返回成功（不等待后台处理），文档状态为「处理中」。
2. **假如** 后台解析、切分、向量化全部成功，**当** 处理完成，**那么** 文档状态更新为「就绪」，且问答链路可以检索命中该文档内容。
3. **假如** 后台任一环节失败，**当** 处理结束，**那么** 文档状态更新为「失败」，并记录可读的失败原因，不产生部分可用的混乱状态。

---

### 用户故事 2 - 查看知识库列表与处理状态（优先级：P2）

管理员查看知识库列表，看到每份文档的名称、上传时间与处理状态；失败文档能看到原因，便于重传或排查。

**优先级理由**：状态可观测是异步任务可用性的前提，但可在入库链路稳定后补充，故为 P2。

**独立测试**：上传多份文档（含一份故意失败的文件），可独立验证：列表正确展示每份文档的名称、上传时间与状态；失败文档展示可读原因。

**验收场景**：

1. **假如** 知识库中存在多份文档，**当** 管理员查看知识库列表，**那么** 列表展示每份文档的名称、上传时间与状态（处理中 / 就绪 / 失败）。
2. **假如** 某份文档处理失败，**当** 查看该文档详情，**那么** 展示可读的失败原因，用户可据此重新上传。

---

### 用户故事 3 - 删除文档并级联清理（优先级：P3）

管理员删除一份文档，系统同步清理原始文件、文档元数据与全部向量切片，删除后该文档内容不再被检索命中。

**优先级理由**：删除与一致性保障在文档可管理后补充，但属于合规必需（宪法硬性约束），故为 P3。

**独立测试**：删除一份已就绪文档，可独立验证：知识库列表中该文档消失、删除后问答链路检索不再命中其内容。

**验收场景**：

1. **假如** 存在一份已就绪文档，**当** 管理员删除它，**那么** 原始文件、文档元数据与全部向量切片均被清理，列表中不再出现该文档。
2. **假如** 文档已被删除，**当** 用户发起问答，**那么** 检索结果 100% 不再命中已删除文档的内容。

---

### 边界情况

- 上传不支持的文件格式（如 `.exe`、`.zip`）—— 应被拒绝并给出明确提示，不进入后台处理。
- 上传空文件（0 字节）或仅含空白字符的文档 —— 应被拒绝并提示，避免入库无意义内容。
- 超大文档或超过大小限制的文件 —— 应被拒绝或提示，不阻塞系统。
- 上传处理中的文档再次操作（删除/重传）—— 应给出可预期的结果（如取消或等待处理完成）。
- 同一文件重复上传 —— 应允许作为独立文档入库（v1 不做内容去重），避免歧义。
- 向量化过程中部分切片失败 —— 应判定整份文档处理失败并回滚已写入切片，不留下半成品。
- 删除请求与解析任务并发 —— 应保证级联清理的一致性，不残留孤儿切片。

## 需求 *(必填)*

### 功能需求

- **FR-001**：系统 MUST 支持上传 txt 与 markdown 文档；pdf 为可选扩展能力，v1 不承诺。
- **FR-002**：系统 MUST 在上传后立即返回成功，文档解析、切分、向量化 MUST 在后台异步执行，不得阻塞上传接口。
- **FR-003**：系统 MUST 为每份文档维护状态机：`处理中 / 就绪 / 失败`；处理结果必须收敛到「就绪」或「失败」。
- **FR-004**：系统 MUST 在后台完成文本抽取 → 文本切分 → 向量化 → 写入知识库的完整入库流程。
- **FR-005**：系统 MUST 建立每份文档与其所有切片的关联索引，支持按文档级联定位切片。
- **FR-006**：系统 MUST 提供知识库列表，展示文档名称、上传时间、处理状态；失败文档 MUST 展示可读失败原因。
- **FR-007**：系统 MUST 拒绝不支持的文件格式与空文件，并给出明确提示，不进入后台处理。
- **FR-008**：系统 MUST 在删除文档时同步清理原始文件、文档元数据与全部向量切片；删除后该文档内容 MUST 立即不再被检索命中。
- **FR-009**：知识库管理操作（上传 / 删除 / 查看）MUST 仅对已认证且有权限的用户开放。
- **FR-010**：文档大小上限 MUST 可配置（默认 20MB），超限上传 MUST 被拒绝并提示。
- **FR-011**：任一处理环节失败 MUST 导致整份文档判定为失败，并清理已产生的部分写入，避免半成品状态。

*未明确项已在「假设」中给出默认值，无需 [NEEDS CLARIFICATION]。*

### 关键实体

- **KnowledgeDoc（知识库文档）**：已上传文档的元数据；含文档名称、上传时间、处理状态（处理中/就绪/失败）、失败原因、原始文件引用。
- **ContentChunk（知识切片）**：文档切分后的文本片段；含切片文本、向量、关联文档 id、片段摘要，供问答链路检索。
- **ParseTask（解析任务）**：后台异步处理单元；承载解析→切分→向量化的执行状态与结果，驱动文档状态流转。

## 成功标准 *(必填)*

### 可度量结果

- **SC-001**：文档上传接口在 2 秒内返回成功，用户无需等待后台处理即可继续操作。
- **SC-002**：典型文档（如 100KB 以内的 txt/md）从上传到「就绪」在 2 分钟内完成。
- **SC-003**：所有合法格式（txt/md）的文档均能完成解析入库，不出现非「就绪」即「失败」之外的状态。
- **SC-004**：知识库列表 100% 准确反映每份文档的当前处理状态，无状态卡死（长时间停留「处理中」）。
- **SC-005**：就绪文档可被问答链路检索命中（与 001-RAG 端到端联动验证）。
- **SC-006**：删除文档后，该文档内容在检索中的命中率降为 0，且不残留孤儿向量切片。
- **SC-007**：失败文档 100% 展示可读原因，管理员无需技术排查即可判断问题（如格式不支持、文件损坏）。

## 假设

- 知识库仅由已认证且有权限的用户（管理员角色）管理；普通客服用户不可上传或删除（见宪法「安全与合规」）。
- txt 与 markdown 为必选支持格式；pdf 解析为可选加分项，v1 交付不承诺（对应初步方案「可选 pdf 解析」）。
- 单文件大小上限可配置，默认 20MB；超限拒绝。
- 上传的原始文件先保存在本地磁盘；生产环境可切换为对象存储（见宪法「开发流程与质量门槛」的组件切换要求）。
- 异步处理使用 FastAPI `BackgroundTasks` 进程内后台任务（Web 进程同事件循环执行，免 Redis/Celery）；配套「僵尸任务清扫」双层兜底防卡死（启动清扫 + 运行期 `asyncio.create_task` 周期循环）。实现细节不影响本规格验收行为；未来如需跨进程扩展可切换到 Celery + Redis（`core/async_tasks.py` 薄接口预留，见 research §1）。
- 文本切分参数（chunk_size、chunk_overlap）为可配置项，具体取值属调优范围（见初步方案 §9 待细化项）。
- v1 对重复上传同一文件不做内容去重，视为独立文档。
- 文档删除为事务性级联清理，保证「原始文件 + 元数据 + 向量切片」一致，删除后立即生效。
