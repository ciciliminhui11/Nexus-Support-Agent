# 研究记录：知识库管理

**日期**：2026-08-29 | **特性**：[spec.md](spec.md)

本文件记录 Phase 0 对技术上下文 unknowns / 依赖 / 集成的研究结论，统一为「决策 / 理由 / 备选方案」。

## 1. 异步任务方案（FastAPI BackgroundTasks + 进程内周期清扫）

> **修订（2026-08-31）**：按需求决定，异步任务由 v1/当前已落地的 Celery + Redis 改为 **FastAPI `BackgroundTasks` 进程内后台任务**。理由：Redis/Celery 部署较复杂（本机需另装 Redis），不适合 demo 阶段；后台任务进程内执行零额外依赖，后续需要再扩展回 Celery。`core/async_tasks.py` 薄接口保留，内部改为 `BackgroundTasks.add_task` 提交。配套「僵尸任务清扫」双层兜底防卡死。

- **决策**：采用 FastAPI `BackgroundTasks` 在 Web 进程同事件循环内执行「解析→切分→向量化→入库」。任务主体 `process_document` 于 `app/services/knowledge/pipeline.py`（函数式，非 `@celery_app.task`），提交经 `core/async_tasks.py::run_in_background` → `BackgroundTasks.add_task(process_document, doc_id)`，HTTP 先返回（FR-002）。
- **僵尸任务清扫（SC-004 防卡死）**：`process_document` 自开 `SessionLocal()`，与请求会话解耦。配套双层兜底：
  1. **启动清扫**：`main.py` lifespan 启动时调 `sweep_zombie_tasks()` → `mark_stale_processing_timeout()`，把上次进程崩溃遗留的超时「处理中」任务/文档置失败（进程崩溃即新解释器启动，遗留必然僵尸）。
  2. **运行期周期清扫**：`main.py` lifespan 内 `asyncio.create_task` 启动一个内部循环，每隔 `parse_timeout_seconds` 调一次 `mark_stale_processing_timeout()`，处理进程长期存活期间的任务崩溃/卡死（不需要 celery-beat/APScheduler）。
- **理由**：上传接口立即返回（FR-002）、进程内执行零外部依赖（免 Redis/Celery，demo 友好）；抽象层（async_tasks.py）早已预留，未来扩回 Celery 仅改提交实现；「进度内崩溃留僵尸」这一 BackgroundTasks 固有缺陷由双层清扫兜底，满足 SC-004 无卡死；单进程 demo 场景语义足够。
- **备选方案**：曾用/已落地 Celery 5 + Redis（broker / 结果后端均 Redis）→ 任务解耦出 Web 进程、可独立扩展，但需另装 Redis、Windows 下 worker 须 `-P solo`，对 demo 过重；同步阻塞 → 违背宪法原则四（异步化硬性要求）。未来任务量上升或需跨机扩展时，可循本备选扩回 Celery，`run_in_background` 薄接口无需改动。

## 2. 文本切分策略（txt / md）

- **决策**：分块策略按文档类型差异化设计，并保留固定长度兜底：
  - **Markdown（常见问题 FAQ.md）**：按 `## / ###` 标题层级切分，一个完整章节为一个 chunk，保证语义完整，避免把一条政策/一个 FAQ 条目从中间切断；标题缺失或章节超长时，按固定长度兜底。
  - **txt（公司产品介绍.txt、退换货政策.txt）**：先用递归分块粗切，块内部再做精细语义二次切分——用 embedding 相似度检测语义断点，在语义突变处切分；语义均匀无法收敛时，按固定长度兜底。
  - 固定长度兜底参数：`chunk_size=500` 字、`chunk_overlap=80` 字；切分逻辑自研（`splitter.py`），参数通过配置读取。
- **理由**：分块决定 RAG 上限，分块切得差，后面检索、Prompt 再怎么调都很难补救。FAQ.md 按 `## / ###` 章节切分，一条政策/一个 FAQ 条目完整成块，检索命中即拿到完整语义，避免把政策拦腰切断；txt 为连续叙述文本，先递归粗切再按语义断点二次切分，能在大段文本语义转折处拆块，检索质量显著高于固定字符硬切。固定长度兜底保证任何输入都收敛为有限数量的块。
- **备选方案**：固定字符硬切 → 易切断语义单元（把一条政策从中间切开）；LangChain RecursiveCharacterTextSplitter → 引入黑盒依赖，违背原则一（可解释性要求）；纯语义二次切分不用兜底 → 标题/结构缺失或语义均匀的文档无锚点可切，需固定长度兜底收敛。

## 3. 向量化与写入 Chroma（性能 + 增强元数据 + Embedding 增强）

- **决策**：bge-m3 单模型实例复用；切片分批向量化（batch=16）后一次性写入 Chroma collection。每个 chunk 除文本外挂**增强元数据体系**（不止 doc_id）：
  ```json
  {
      "source_file": "退换货政策.txt",
      "section": "7天无理由退换条件",
      "heading_path": ["退换货政策", "7天无理由退换条件"],
      "category": "aftersale",
      "version_date": "2026-08-01",
      "source_priority": 2,
      "chunk_index": 12
  }
  ```
  - `version_date`：文档版本时间，知识冲突时时间优先；
  - `source_priority`：来源优先级（政策原文 > FAQ 汇总文档）；
  - `category`：业务分类，支持检索时做元数据过滤。
  同时保留 `doc_id`（关联 MySQL 文档）、`snippet`（片段摘要，取切片首部去格式化文本）；向量库内部 ID 用 `doc_id-chunk_index` 确定性生成，便于按 `doc_id` 定位删除。
  **chunk 文本增强**：向量化前把父标题/章节标题拼到文本开头再 Embedding——短 chunk（单条 FAQ）语义信息少，注入标题显著提升检索匹配，如 `【退换货政策-7天无理由】7天无理由要求商品未拆封……`。
  **表格内容预处理**：表格不能直接喂 Embedding，入库前转换为自然语言描述再切片。实施优先级：✅MVP 可做，改动集中在知识库异步解析任务，不改动问答主链路。
- **理由**：分完块后每个 chunk 不能只存文本，增强元数据支撑检索时的元数据过滤（category）与知识冲突裁决（version_date 时间优先、source_priority 来源优先），heading_path 保留章节路径便于溯源；标题注入补足短 chunk 语义稀疏，显著提升检索匹配；表格结构化内容转自然语言后 Embedding 才有语义。确定性 ID + metadata.doc_id 满足宪法「可追溯索引对」与 FR-005/FR-008 按文档级联定位；分批向量化利用 GPU/CPU 批处理，100KB 文档（约 200 切片）可在 2 分钟内完成（SC-002）。
- **备选方案**：仅存 doc_id → 无法做元数据过滤与冲突裁决，检索只能靠纯向量相似度；只向量化表格原文 → 表格行列结构对 Embedding 是噪音，检索命中率低；逐条写入 → 慢且碎片化；随机内部 ID 仅靠 metadata 过滤 → 删除时全量扫描过滤不可靠。

## 4. 失败处理与回滚（FR-011）

- **决策**：处理流水线（`pipeline.py`）用事务边界包装：任一步骤抛错即标记文档 `失败` 并记录可读 `fail_msg`，同时按 `doc_id` 清理该文档已写入的向量切片；已入库的切片在文档状态未到「就绪」前不参与检索（检索只过滤「就绪」文档的 doc_id）。
- **理由**：规格边界要求「部分切片失败 → 整份失败并回滚，不留下半成品」；检索端过滤就绪状态是双保险，避免失败文档的半成品被问答命中。
- **备选方案**：保留半成品切片 → 检索命中不完整内容，违反 FR-011 与宪法质量门槛；仅标记失败不清理 → 残留孤儿向量。

## 5. 状态机与「处理中」卡死防护（SC-004）

- **决策**：`KnowledgeDoc.status` 状态机 `处理中 →（就绪|失败）`，单向收敛；后台任务启动前写入「处理中」，完成/异常时写入终态；配合超时守卫（`mark_stale_processing_timeout`，超时如 10 分钟判定失败）：双层触发（启动清扫 + 运行期 `asyncio.create_task` 周期循环，见 §1），保证进程崩溃/任务卡死也能收敛，不长期停留「处理中」。
- **理由**：SC-004 要求 100% 准确反映状态、无卡死；超时守卫保证异常中断（进程崩溃）也能收敛，不长期停留「处理中」。
- **备选方案**：仅依赖任务自身完成回调 → 进程崩溃时状态永久「处理中」，违反 SC-004；引入心跳表 → v1 过重，超时守卫足够。

## 6. 上传校验（格式 / 空文件 / 大小）

- **决策**：`validator.py` 在接口层同步校验：扩展名白名单（`.txt`/`.md`）、MIME 兜底、文件大小 ≤ 配置上限（默认 20MB）、非空文件（size>0 且去除空白后非空）；任一不通过返回 4xx 明确提示，不进入后台。
- **理由**：FR-007/FR-010 要求拒绝不支持的格式/空文件/超限并明确提示；同步校验避免无效任务进后台空转。
- **备选方案**：全部交给后台 → 无效文件也建任务、浪费资源且状态混乱；仅看扩展名 → 内容伪造穿透，加 MIME 与空内容兜底。

## 7. 删除级联一致性（FR-008 / 边界：删除与解析并发）

- **决策**：删除接口在事务内执行：先按 `doc_id` 删除 Chroma 切片（确定性 ID 批量删除）→ 删除 MySQL 元数据 → 删除本地原始文件；三步在同一事务协调，任一失败回滚；对「处理中」文档的删除，标记取消信号，后台任务完成后检测取消标记则不重写状态、直接完成清理。
- **理由**：宪法原则五要求「删除文档必须同步删除对应向量切片、删除后立即不再命中」；并发边界（删除 vs 解析）通过取消标记保证不残留孤儿切片。
- **备选方案**：无协调直接删 MySQL → 向量切片残留、问答仍命中；强制等处理完成 → 用户体验差、边界复杂。

## 8. 权限模型（FR-009）

- **决策**：上传/删除/列表接口要求 JWT 鉴权（003 特性提供中间件），并校验角色为「管理员」；普通用户查询列表返回空或仅只读（v1 约定：管理员专属，详见 003 契约的角色模型）。
- **理由**：宪法安全与合规要求管理后台数据查询/统计必须鉴权授权；规格假设「知识库仅管理员管理」。
- **备选方案**：任何人可管理 → 违反安全要求；v1 不加角色 → 后续返工。

## 9. 测试策略

- **决策**：pytest；单元测试覆盖校验/切分/状态机；集成测试用真实 Chroma（临时目录）+ SQLite 模拟 MySQL，覆盖上传→就绪全链路、失败回滚（注入解析异常）、删除级联（删除后检索命中率 0）、并发删除与解析。
- **理由**：宪法要求「文档解析→向量化入库」关键链路集成测试（必须）；mock 化异常使失败路径可确定复现。
- **备选方案**：仅单元测试 → 无法验证真实向量化与 Chroma 级联；直接依赖真实 MySQL → CI 不稳定。
