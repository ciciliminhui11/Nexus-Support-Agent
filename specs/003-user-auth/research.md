# 研究记录：用户鉴权

**日期**：2026-08-29 | **特性**：[spec.md](spec.md)

本文件记录 Phase 0 对技术上下文 unknowns / 依赖 / 集成的研究结论，统一为「决策 / 理由 / 备选方案」。

## 1. 密码哈希算法

- **决策**：采用 bcrypt（passlib 封装），`rounds=12`，每用户随机盐；存储格式 `bcrypt$...` 含盐与迭代，校验时库内比对。
- **理由**：宪法与 FR-003 要求「不可逆方式存储（加盐哈希）」；bcrypt 自带随机盐、自适应代价（抗 GPU/ASIC 爆破）、业界成熟（OWASP 推荐）；SC-004 合规核验可通过库内容不可还原验证。
- **备选方案**：SHA-256 + 固定盐 → 无代价因子、爆破成本低；MD5 → 已破解不适用；argon2 → 更强但本地 PyPI 依赖稍重，作为备选记录。

## 2. 令牌方案（JWT）

- **决策**：JWT HS256 签名，密钥取自环境变量 `JWT_SECRET`（≥32 字节）；载荷含 `sub`（user_id）、`role`、`account_type`、`iat`、`exp`（默认 24h，可配置 `jwt_expire_hours`）；全站受保护接口经 `api/deps.py` 依赖解码校验 `sub`/`exp`。
- **理由**：宪法安全与合规明确「采用 JWT 鉴权」；无状态令牌适合多后端实例；有效期默认 24h 与规格假设一致；密钥仅存服务端环境变量符合「密钥仅存服务端」。
- **备选方案**：服务端 session（Redis 存储）→ 需会话存储与吊销服务，v1 规格明确不做；opaque token → 需查库校验、慢；JWT RS256 → 密钥管理复杂，v1 单服务用 HS256 足够。

## 3. 登录失败防护（FR-010）

- **决策**：按「账号标识 + 来源 IP」维度记录连续失败次数；失败次数 N 次（默认 5）后触发递增延迟（2^N 秒，封顶 300 秒）；登录成功后计数清零；成功路径不受影响。
- **理由**：FR-010 要求「临时锁定或递增延迟」；递增延迟比硬锁定对真实用户更友好（避免误锁），同时显著抬高暴力破解成本；按账号+IP 双维度避免单维度绕过。
- **备选方案**：固定锁定账号 N 分钟 → 可被攻击者故意触发锁死他人（DoS）；仅按 IP → 分布式攻击绕过；不防护 → 违反 FR-010。

## 4. 防账号枚举（FR-006）

- **决策**：登录失败统一返回 `{ "code": "invalid_credentials", "message": "手机号/邮箱或密码错误" }`，不区分「账号不存在」与「密码错误」；注册仍区分「标识已占用」（注册场景枚举风险低且业务需要明确提示）。
- **理由**：FR-006 明确要求统一提示防枚举；规格边界情况亦要求「账号不存在与密码错误返回相同提示」。注册提示占用是注册流程的标准行为，不构成登录枚举面。
- **备选方案**：区分「账号不存在」→ 泄露账号存在性，违反 FR-006/SC-006。

## 5. 手机号 / 邮箱 / 密码校验

- **决策**：手机号默认中国大陆 11 位（`^1[3-9]\d{9}$`，`phone_regex` 可配置）；邮箱用标准正则 + `@`/域名存在校验；密码最小 8 位（`min_password_length` 可配置），空/全空白拒绝；账号标识二选一（`account_type`：phone / email）。
- **理由**：FR-002/FR-009 与规格假设对齐；正则可配置满足「格式规则可配置」假设。
- **备选方案**：不校验格式 → 数据脏、登录无法匹配；强制邮箱+手机号双字段 → 违反「二选一」假设。

## 6. 每日配额联动（FR-008）

- **决策**：UserQuotaDaily 以 `(user_id, stat_date)` 唯一键按自然日计数，系统配置时区切日；001 在问答入口负责「校验 + 原子递增」，003 提供 `quota.py` 查询（已用/剩余 = limit - count）供 `GET /api/auth/me` 展示；配额上限配置 `daily_quota_limit` 默认 100。
- **理由**：规格要求「配额计数与问答行为一致」且 003 提供查询能力；计数写入收敛在 001 单点（原子 UPDATE），003 只读，避免双写竞态；按自然日（配置时区）跨日自动重置符合假设。
- **备选方案**：各自独立计数表 → 双写不一致；内存计数 → 重启丢失。

## 7. 角色模型

- **决策**：User 表增加 `role` 字段（`user`/`admin` 两档），管理员由配置预置（`ADMIN_ACCOUNT` 环境变量指定的账号在启动或注册时置为 admin，或用 seed 脚本）；`core/roles.py` 提供 `require_admin` 依赖，002 知识库管理复用。
- **理由**：规格假设「角色 v1 仅普通用户/管理员，管理员由配置预置」；002 FR-009 需要角色校验；依赖抽象让各特性直接复用。
- **备选方案**：无角色字段 → 无法支撑 002 的管理员隔离；数据库 seed 硬编码 → 明文密码/凭据入仓风险，用环境变量预置更安全。

## 8. 测试策略

- **决策**：pytest；单元测试覆盖哈希不可逆/加盐、JWT 签发过期无效、校验规则、递增延迟；集成测试覆盖注册→登录→受保护访问全链路、配额与问答联动（构造提问使计数变化后查询 `me`）、并发登录互不干扰。
- **理由**：宪法要求关键链路集成测试；鉴权是安全边界，须覆盖无效/过期令牌、防枚举、失败防护等边界。
- **备选方案**：仅单元测试 → 无法验证依赖注入与实际路由鉴权；跳过失败防护测试 → 安全边界失守风险。
