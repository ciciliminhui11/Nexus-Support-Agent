# 研究记录：用户反馈

**日期**：2026-08-29 | **特性**：[spec.md](spec.md)

本文件记录 Phase 0 对技术上下文 unknowns / 依赖 / 集成的研究结论，统一为「决策 / 理由 / 备选方案」。

## 1. 反馈存储模型（upsert，最后为准）

- **决策**：Feedback 表以 `UNIQUE(message_id, user_id)` 为唯一键；提交用「先查后插 / 命中则更新」的 upsert（SQLAlchemy `insert ... on_duplicate_key_update` 或查改事务），覆盖 `feedback_type`、`feedback_text`、`update_time`。
- **理由**：FR-006 要求「重复反馈覆盖更新，最后为准」；唯一键保证一条消息同一提交者只有一条记录（规格假设），upsert 原子化避免并发下重复行/竞态。
- **备选方案**：每次插入新行、查询取最新 → 违反「一条记录」假设、数据冗余；无唯一键 → 重复提交产生多条记录，行为不可预期。

## 2. 消息校验（角色 + 归属 + 存在性）

- **决策**：提交前按 message_id 查消息 → 不存在返回 404 → 定位其会话并断言归属当前用户（越权 404/403，不泄露存在性）→ 断言 `role == 'ai'`（用户消息返回 400）→ 通过后写入。
- **理由**：FR-003 仅 AI 可反馈 + FR-009 越权拒绝 + 边界「不存在消息拒绝」；复用 004 的会话归属校验保证隔离；对非 AI 消息明确 400 提示（验收场景明确要求）。
- **备选方案**：不校验 role → 用户消息被反馈，违反 FR-003/SC-003；仅查消息不查归属 → 他人会话消息可被反馈，违反 FR-009。

## 3. 校验规则（类型必选 + 文字长度）

- **决策**：请求体 `feedback_type` 枚举 `like`/`dislike`，必填（无类型返回 400）；`feedback_text` 可选，长度 ≤ `feedback_max_length`（默认 200，可配置），恰好等于上限通过（边界值）；空白文字视同未填写。
- **理由**：FR-008 必须至少选一种类型；FR-007 长度限制默认 200 可配置；边界值（恰好 200）应通过符合规格边界要求。
- **备选方案**：类型可空 → 违反 FR-008；无长度限制 → 恶意超长文本入库，违反 FR-007。

## 4. 反馈独立存储（消息删除后保留）

- **决策**：Feedback 表外键 `message_id` **不做** `ON DELETE CASCADE`，且存储消息所属会话快照不必要；反馈记录独立留存，删除消息/会话不影响反馈数据（供统计）。
- **理由**：规格边界与假设明确「反馈独立存储，消息删除后保留，供统计」；管理后台统计（加分项）依赖历史反馈数据，级联删除会丢失质量数据。
- **备选方案**：`ON DELETE CASCADE` → 删消息即丢反馈，违反假设；冗余会话字段 → 增加复杂度，v1 统计仅需消息与类型。

## 5. 查询能力（SC-005 数据基础）

- **决策**：提供 `GET /api/message/{id}/feedback` 返回该消息的反馈（含提交者、类型、文字、时间），供前端展示「我是否反馈过」；全量统计接口归加分项（管理后台），不在本特性。
- **理由**：FR-005 要求「可按消息关联查询」；前端重入需要展示当前用户对该消息的反馈状态；统计接口留待加分项扩展（数据字段已齐全：类型/文字/消息/时间/提交者）。
- **备选方案**：只写不读 → 无法满足 FR-005；本特性就做全量统计 → 超范围（规格明确为加分项）。

## 6. 测试策略

- **决策**：pytest；单元测试覆盖类型必选、长度边界（199/200/201）、角色校验、upsert；集成测试覆盖提交→覆盖更新→隔离拒绝→按消息查询。
- **理由**：宪法要求关键链路集成测试；覆盖更新一致性（SC-004）、隔离（SC-006）为可度量合规项。
- **备选方案**：仅单元测试 → 无法验证真实 upsert 与归属链路。
