# AI 智能客服系统‑初步技术方案.md

> 
> 文档用途：供 AI / 开发人员读取、进一步拆解细化、输出数据库设计、接口、RAG 链路、代码目录、风险点；基于笔试题需求做结构化技术方案，保留全部业务约束、边界条件、可选加分需求。

## 1 项目概述

### 1.1 项目目标

构建企业级基于 LLM 的 RAG 智能客服系统，完整覆盖：用户会话管理、知识库文档解析 & 向量化存储、向量检索、Prompt 组装、大模型调用、SSE 流式回答输出、答案来源引用、用户反馈统计；支持多轮对话，对检索空、LLM 超时、限流、上下文超长、幻觉等工程问题做处理；包含基础必选功能与多项扩展加分特性。

### 1.2 业务约束（硬性规则，不可忽略）

1. 单条用户提问最大长度：500 字
2. 用户每日提问次数上限：可配置，默认 100 次 / 用户 / 天
3. 检索不到知识库片段时禁止编造内容，输出兜底话术
4. 回答输出必须流式（SSE 优先，不允许全部生成完成再返回）
5. 每次 AI 回答附带引用来源：文档名称 + 片段摘要
6. 多轮对话携带最近 N 轮历史上下文，N 可配置
7. LLM、向量检索全部在后端完成；前端禁止直接调用大模型 API
8. 支持文档：必选 txt、md；可选 pdf 解析
9. 删除知识库文档，同步删除对应向量库向量数据

### 1.3 必做功能清单

1. 用户模块：注册、登录（手机号 / 邮箱 + 密码）
2. 会话 Session：创建会话、会话列表、会话详情历史消息
3. 用户反馈：点赞 / 踩、可选文字反馈
4. 知识库：文档上传、文档解析、向量化入库、知识库列表（状态：处理中 / 就绪 / 失败）、文档删除
5. RAG 问答链路：问题输入→Embedding 向量→向量检索→Prompt 拼接→LLM 调用→SSE 流式返回，附带知识来源
6. 多轮对话、输入长度校验、每日次数限流、空检索兜底、异常捕获（LLM 超时、API 限流）

### 1.4 可选加分功能清单

1. 用户问题意图识别（产品咨询 / 售后 / 闲聊 / 投诉），会话记录标注意图分类
2. AI 回答结束自动生成 2‑3 条追问建议
3. 管理后台：全量会话查询、反馈统计、日均问答量图表
4. 多知识库路由：多个知识库，自动路由匹配最相关知识库
5. 检索结果优化策略：大量检索片段下防止注意力稀释、减少幻觉；分层摘要、优先级排序、分步校验
6. AI Agent 任务拆解（终极挑战）：根据业务需求 + 系统文档，判断改动哪些微服务、并行任务、依赖顺序；输出拆解流程，可选代码实现

## 2 技术选型初步方案

> 
> 说明：给出推荐选型，同时给出备选；后续细化阶段可替换，所有第三方 API 密钥使用环境变量配置，禁止硬编码。

### 2.1 前端

- 推荐：Vue3 + TypeScript + Element‑Plus
- 备选：React + TypeScript + Ant‑Design
- 通信方案：
  - 普通接口：RESTful HTTP
  - 流式问答：SSE Server‑Sent Events

### 2.2 后端

- 推荐：Python FastAPI
> 
> 理由：异步原生，对 SSE 流式输出友好，AI 生态库丰富，开发效率高；
- 备选：Java SpringBoot

**核心依赖：**

- web：fastapi、uvicorn
- 文件解析：python‑docx、PyMuPDF（pdf 可选）
- 向量库：Chroma（本地文件模式，开发简单无需额外服务）；备选 Qdrant/Milvus
- Embedding：bge‑m3（本地开源 embedding，不依赖外部 API）；备选 OpenAI text‑embedding
- LLM 接入：Ollama 本地 Qwen2；备选通义千问 API、Groq 免费 API
- ORM：SQLAlchemy
- 数据库：MySQL 8.0
- 鉴权：JWT 实现登录认证
- 任务：文档解析 & 向量化为 CPU IO 耗时任务，采用后台异步任务（BackgroundTasks / Celery，文档量大选 Celery）

> 
> 重要：文档上传之后解析、切分、向量化是耗时操作，不能同步阻塞 http 接口；接口返回成功，后台异步处理，数据库记录文档状态：处理中 / 就绪 / 失败。

### 2.3 存储分层

1. **MySQL**：存储业务元数据：用户表、会话 session 表、消息记录表、知识库文档元数据表、用户反馈表、系统配置表（每日提问上限、上下文轮数 N、检索 top‑k、相似度阈值）
2. **向量数据库 Chroma**：存储文档切片向量；向量库内部 ID 和 MySQL 知识库文档 ID 做关联；删除文档时，根据关联 ID 批量删除向量库切片。
3. **文件存储**：上传原始文档，本地磁盘存储（开发阶段）；生产可替换对象存储。

### 2.4 RAG 实现方式

可以使用 LangChain 做辅助工具，但**核心链路需要可控可读**；禁止直接调用高阶封装链而不理解内部逻辑；允许手动实现切分、embedding、检索、prompt 组装便于调优排错。

## 4 核心业务流程简述

### 4.1 知识库文档上传流程

1. 用户上传文档文件，http 接口接收文件
2. 保存原始文件，MySQL 插入知识库文档记录，状态 = 处理中
3. 提交后台异步任务：
   1. 根据后缀解析文档文本
   2. 文本分割成 chunk 片段
   3. 调用 Embedding 模型生成向量
   4. 将 chunk 文本、向量、关联文档 ID 存入向量库
   5. 成功：更新文档状态 = 就绪；失败：更新状态 = 失败，记录失败原因

### 4.2 用户问答完整 RAG 流程

1. 用户登录，携带 JWT；发起问答请求（SSE 连接），传入 session_id、用户 question
2. 后端校验：
   - 问题长度≤500 字
   - 用户今日提问次数是否到达上限，超限直接返回错误
3. 读取该 session 最近 N 轮历史对话消息
4. 用户 question 做 embedding 向量
5. 向量库检索：设置相似度阈值、top‑k，过滤低于阈值的片段
6. 判断检索结果：
   - 无有效片段：组装兜底 prompt，返回兜底回答，标记无参考来源；结束
   - 有片段：保留检索片段，记录来源文档名称、片段摘要
7. 检索结果后处理（加分项：排序、分层摘要）
8. 上下文窗口处理：历史消息 + 检索内容总长度超限，执行截断策略，丢弃最早历史消息
9. 拼接 System Prompt + 检索知识库上下文 + 用户历史对话 + 当前用户问题
10. 请求 LLM 流式接口；捕获异常：超时、限流、服务不可用
11. 通过 SSE 逐块返回数据：
   - `data`事件：返回模型生成 token
   - `meta`事件：传递引用来源信息
   - `finish`事件：会话结束标记
   - `error`事件：错误信息
12. 保存用户提问消息、AI 完整回答消息到 MySQL 消息表；如果开启意图识别，写入意图标签字段
13. （可选加分）生成 2‑3 条追问建议，通过 finish 事件一并下发

> 
> 关键点：向量检索、LLM 调用全部后端执行；SSE 返回元信息（来源）和 token 流。

## 5 关键工程问题应对方案（初步思路，后续细化落地）

> 
> 对应题目重点考察：检索为空、上下文超长、LLM 幻觉、大量检索片段信息过载

1. **检索为空**

- 向量相似度阈值过滤，低于阈值视为没有相关知识；返回预设兜底话术：`抱歉，知识库中没有找到相关信息，请换个方式提问或者联系人工客服。`，禁止模型编造。

2. **上下文超长**

- 配置最大上下文 token 上限；
- 策略：优先截断最早多轮对话历史；保留检索知识库片段；当知识库片段过大，做摘要压缩，而不是直接丢弃知识。

3. **LLM 幻觉抑制**

- System Prompt 强约束：必须严格基于提供知识库内容回答；知识库没有信息不要编造；明确要求回答中标注引用来源；
- 检索结果携带元信息，要求模型只能使用给定材料；
- 兜底逻辑：检索不到直接不走生成，输出固定文本。

4. **大量检索片段‑注意力稀释 / 信息过载（加分）**
初步设计思路：
5. 检索召回更多候选，做重排序 Rerank；
6. 知识片段打上优先级标签；
7. 分层摘要：把相似片段合并，压缩冗余；
8. Prompt 内对知识做编号；指令要求模型回答必须引用编号来源；
9. 增加后校验步骤：模型输出完成后二次校验输出内容是否不在知识库范围，发现幻觉标记提示。
10. **异常处理**

- LLM 调用超时：设置 http 超时时间；捕获超时异常，SSE 推送错误事件；
- API 限流：捕获 429，返回友好提示；
- Embedding 模型异常、向量库异常：日志记录，返回业务错误。

6. **用户每日次数限制**
MySQL 记录用户每日提问计数；每次问答前校验；计数落库。

## 6 数据库初步设计要点（待细化 ER 图 + 完整表结构）

核心表清单：

1. `user` 用户表：id、账号类型 (手机号 / 邮箱)、密码哈希、创建时间
2. `session` 会话表：id、user_id、会话标题、创建时间
3. `message` 消息表：id、session_id、role (user/ai)、content、intent_label (意图标签，可 null)、reference_source (json 存储引用来源)、create_time
4. `knowledge_doc` 知识库文档元数据表：id、doc_name、file_path、status (处理中 / 就绪 / 失败)、upload_time、fail_msg
5. `feedback` 用户反馈表：id、message_id、feedback_type (点赞 / 踩)、feedback_text
6. `system_config` 系统配置表：配置项 key‑value；存储每日提问上限、上下文轮数 N、向量 top‑k、相似度阈值等

> 
> 向量库侧：每个切片存储：page_content、metadata`{"doc_id":知识库文档id}`；通过 doc_id 关联 MySQL 的 knowledge_doc。删除文档时，向量库根据 metadata.doc_id 批量删除。

## 7 API 接口规划（待细化请求响应示例、SSE 事件格式）

### 普通 http 接口

1. `POST /api/auth/register` 用户注册
2. `POST /api/auth/login` 用户登录 返回 JWT token
3. `POST /api/session` 创建会话
4. `GET /api/session/list` 获取用户会话列表
5. `GET /api/session/{id}/messages` 获取会话全部消息
6. `POST /api/knowledge/upload` 上传知识库文档
7. `GET /api/knowledge/list` 获取知识库文档列表
8. `DELETE /api/knowledge/{id}` 删除知识库文档
9. `POST /api/message/{id}/feedback` 提交反馈点赞 / 踩

### SSE 流式问答接口

`GET /api/chat/stream?session_id=xxx&question=xxx`

> 
> 返回 SSE 流；定义事件：data、meta、finish、error；meta 事件携带知识来源数组。
